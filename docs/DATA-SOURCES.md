# แหล่งข้อมูล (Data Sources)

ระบบดึงข้อมูลจากหน่วยงานรัฐเป็นหลัก แล้วแปลงให้อยู่ในรูปแบบเดียวกัน (`Station` + `Reading` ใน `src/lib/types.ts`)
ทุก adapter อยู่ใน `src/lib/sources/` และมี test ด้วยข้อมูลจริงที่บันทึกไว้ใน `tests/fixtures/`

> ทุก endpoint ของ กทม. เป็น API ภายในที่หน้าเว็บสาธารณะใช้ ไม่ใช่ API ที่เปิดอย่างเป็นทางการ อาจเปลี่ยนได้โดยไม่แจ้ง
> ก่อนเปิดให้บริการสาธารณะ ควรขออนุญาตสำนักการระบายน้ำ กทม. และ สสน. (info_thaiwater@hii.or.th) และแสดงที่มาของข้อมูลทุกหน้า

## ข้อจำกัดเรื่อง IP (สำคัญ)

ทุกโดเมน `*.bangkok.go.th` อยู่หลัง Cloudflare และตอบ 403 (challenge) หรือ timeout กับ IP ต่างประเทศ/ศูนย์ข้อมูล
(ทดสอบแล้วโดยโครงการอื่น: GitHub Actions, Vercel, Cloudflare Workers, Google Apps Script) — จึงต้องมีเครื่องดึงข้อมูลที่อยู่ในประเทศไทย
ดูวิธีติดตั้งใน `docs/DEPLOY.md` ส่วน ThaiWater และ Open-Meteo ดึงจาก cloud ได้ จึงเป็นแหล่งสำรองเมื่อไม่มีเครื่องในไทย

แม้จาก IP ไทยก็ยังเจอ 403 เป็นครั้งคราว (~9–12%) ระบบจึง retry หลัง 5 และ 15 วินาที และอุ่น cookie ด้วยการเปิดหน้า `/water` หนึ่งครั้งเมื่อเจอ 403
ห้ามยิงถี่ — ระบบดึง 1 request ต่อ endpoint ต่อรอบ (ค่าเริ่มต้นทุก 10 นาที)

## กติกาการแปลงข้อมูล (normalization)

- **เวลา**: `/Date(ms)/` ของ กทม. เป็น epoch UTC จริง, ข้อความ `site_timestampTH` เป็นปี พ.ศ. (ไม่ใช้), เวลาของ ThaiWater/Open-Meteo เป็นเวลาไทยไม่มี timezone → ตีความเป็น +07:00
  ค่าที่ลงเวลาในอนาคตเกิน 15 นาทีถูกทิ้ง (เซนเซอร์บางตัวนาฬิกาเพี้ยน)
- **ตลิ่ง**: ใช้ตลิ่งฝั่งที่ต่ำกว่า `min(left_bank, right_bank)`; ค่า ≤ 0 หรือ ≥ 10 ถือว่าไม่มีข้อมูล
  ถ้าสองฝั่งต่างกันเกิน 1 ม. หรือตลิ่งต่ำกว่า 0.3 ม. ถือว่า "ข้อมูลตลิ่งไม่แน่นอน" (`bankUncertain`) และจะไม่ยกระดับเกิน "เฝ้าระวัง" จากค่านี้อย่างเดียว
- **ระยะห่างตลิ่ง** (freeboard) = ตลิ่ง − ระดับน้ำ (ปัดเป็นซม.) ค่าติดลบ = น้ำล้นตลิ่ง
  ที่ประตูระบายน้ำ/สถานีสูบใช้ระดับน้ำด้านในคลอง (`wl_in`) เท่านั้น
- **ค่าพิเศษ**: −99 (≤ −90) = ไม่มีค่า, −2.00 ตรงตัวของ กทม. = เซนเซอร์หลุด, 999999 ของ สสน. = ไม่มีค่า, ระดับน้ำติดลบเป็นเรื่องปกติในคลองที่สูบน้ำออก
- **เกณฑ์ของหน่วยงาน**: เกณฑ์ "เตือนภัย/วิกฤต" ของ กทม. หลายจุดเป็นค่าตั้งต้น (−0.2/0) หรือเป็นซม. (320/450) หรือเป็นระดับควบคุมการระบายน้ำที่ต่ำกว่าตลิ่งมาก
  ระบบจึงใช้ระยะห่างตลิ่งเป็นหลัก และแสดงสถานะของ กทม. เป็นข้อมูลประกอบในวงเล็บ
- **ThaiWater `situation_level`**: 1 = น้ำน้อยวิกฤติ (ไม่ใช่ "ปกติ"), 5 = ล้นตลิ่ง — ระบบไม่ใช้ค่านี้ตัดสิน แต่คำนวณจาก `min_bank` เอง
  `min_bank = 0` / `ground_level = 0` คือไม่ทราบตลิ่ง
- **ฝน**: แถวของ กทม. ที่ `status ≠ 1` เป็นสถานีขัดข้องและมีค่า 0 ปลอม → ไม่นำมาใช้; `rain_1h` ที่ไม่มี key (กรมอุตุฯ/ปภ.) = ไม่ทราบ ไม่ใช่ 0
  `rain_24h` เป็นยอดสะสม 24 ชม. แบบเลื่อน ไม่ใช่รอบ 07:00–07:00 ของกรมอุตุฯ
- **น้ำท่วมถนน**: `chkStatustxt = 'น้ำท่วม'` ใช้ค่า `flood` (ซม.), `'ปกติ'` = 0 ซม., ค่าอื่น = ขัดข้อง (ไม่บันทึก)
- **ข้อมูลค้าง**: ไม่ใช้ค่าที่เก่ากว่า 60 นาที (คลอง), 90 นาที (ฝน), 180 นาที (ถนน) ในการแจ้งเตือน และแสดงเป็นสีเทา "ไม่มีข้อมูลล่าสุด"
- **รวมสถานีซ้ำ**: จุดวัดของ กทม. ที่ สสน. ทวนข้อมูลใช้รหัสเดียวกัน (`canal:WL.xxx.nn`, `rain:RF.xxx.nn`, `road:FL.xxx.nn`)
  ข้อมูลประกอบ (ชื่อ ตลิ่ง) จาก กทม. มีลำดับความสำคัญสูงกว่า

## กล้อง CCTV

- ใช้เฉพาะแหล่งของหน่วยงานรัฐโดยตรง ไม่ใช้ relay ของบุคคลที่สาม (POPNIX, maholan ฯลฯ)
- รูปแบบรายชื่อ `camera_profile` (`id, CameraName, LiveStream, Lat, Long, camera_description`) เดิมรู้จากโค้ดของโครงการอื่นเท่านั้น
  ณ 6 ต.ค. 2569 (probe v3 จากเครื่องในไทย) parser อ่านรายชื่อจริงได้ 876 กล้อง ไม่มีคำเตือน (ไม่มีแถวถูกตัด) — parser ยังยอมรับทั้งตัวเลขและสตริงตัวเลข
  ตัดแถวที่อยู่นอกกรอบ กทม. (13.5–14.1 N, 100.2–100.95 E) และรับเฉพาะที่อยู่สตรีม `rtsp/rtmp/http/https` ที่ไม่เกิน 512 ตัวอักษร
- ที่อยู่สตรีม (`LiveStream`) และลิงก์ในข้อมูล DWR ที่มี user/password ฝังอยู่ **ไม่ถูกส่งออก ไม่ถูกบันทึกใน log และไม่ถูก relay**
- ระบบขอภาพเฉพาะเมื่อมีคนเปิดดู ผู้ใช้เซิร์ฟเวอร์เดียวกันใช้ภาพเดียวกันร่วมกัน มีเพดานต่อชั่วโมงต่อโปรเซส (กล้องเฝ้าระวังน้ำท่วม กทม. 600 ภาพ, กล้องระดับน้ำ สนน. 360 ภาพ, DWR 240 ภาพ —
  บน serverless นับแยกต่อ instance จึงปิดภาพเป็นค่าเริ่มต้นบน Vercel) และเพดานต่อผู้ใช้ (40 ภาพใหม่ต่อ 10 นาที ต่อ IP)
  ส่ง `User-Agent` แบบเบราว์เซอร์ต่อท้ายด้วย `flood-monitor/0.1` และลิงก์หน้า /about (แบบเดียวกับคำขอ กทม. อื่น ๆ — WAF ของหน่วยงานปฏิเสธ
  User-Agent ของเครื่องมือล้วน ๆ) ไม่ปลอม Referer/Origin รับภาพ JPEG, PNG หรือ WebP และตาม redirect เฉพาะภายในโดเมนเดียวกัน ถ้าหน่วยงานตอบ 429 หรือ 403 ซ้ำ ระบบหยุดขอภาพจากแหล่งนั้น 1–60 นาที
- ภาพเก็บในหน่วยความจำเท่านั้น (กทม. ไม่เกิน 15 นาที, DWR ไม่เกิน 1 ชั่วโมง ลบตามอายุอัตโนมัติ) ไม่บันทึกลงดิสก์/ฐานข้อมูล
  ไม่บันทึกว่าใครดูกล้องใด — ค่า hash ของภาพ (ไม่มีข้อมูลภาพ) ใช้ตรวจภาพค้าง เก็บไม่เกิน 2 ชั่วโมงหลังมีคนดูครั้งล่าสุด
- กล้องเฝ้าระวังน้ำท่วม (`bma-floodcam`): ณ 6 ต.ค. 2569 (probe v3 จากเครื่องในไทย) proxy `floodbangkok.bangkok.go.th/api/proxy` ตอบ HTTP 500
  `{"error":"Internal Server Error"}` ภายใน 43–127 ms ทั้ง 2 กล้องที่ทดสอบ (อยู่บนโฮสต์สตรีมเดียวกัน จากทั้งหมด 876 กล้อง) แม้ขอในรูปแบบเดียวกับหน้าเว็บของ กทม. เอง
  (`rtcUrl` + `timestamp`) และหน้าแรกไม่ตั้ง cookie — ปัญหาอยู่ฝั่งหน่วยงาน ไม่ใช่ฝั่งเรา ส่วนกล้องบนโฮสต์สตรีมอื่นยังไม่ได้ทดสอบ
  (probe v4 ลองโฮสต์ละ 1 กล้อง ไม่เกิน 10 โฮสต์) เครื่องที่ยังไม่เคยได้ภาพจากแหล่งนี้จะพักแหล่งนี้เองเมื่อได้ 5xx ติดกัน 8 ครั้ง (แสดงลิงก์แทน 15 นาที แล้วลองใหม่)
- กล้องระดับน้ำ สนน. (`bma-ddscam`): หน้า `cctv.php` ไม่มีรายชื่อแบบอ่านด้วยโปรแกรมได้และเปิดจากต่างประเทศไม่ได้ รายชื่อจึงเป็นตารางในโค้ด
  (`DDS_CAMERAS` ใน `src/lib/sources/cameras/dds.ts`) ทุกเครื่องสร้างเอง (ไม่ต้องใช้เครือข่าย ไม่ relay) และสร้างใหม่ทุก 24 ชม. เพื่อให้ตารางที่แก้แล้วมีผลภายในหนึ่งวัน
  (ตารางในโค้ดไม่ติดเกณฑ์ "รายชื่อหดเกินครึ่ง" — ตัดแถวออกแล้วมีผลในรอบถัดไป)
  - ที่มาของชื่อ ตำแหน่ง และที่อยู่ภาพ: หมุด Leaflet บนแผนที่ของหน้า `cctv.php` เอง (`L.marker([lat, lon]).bindPopup('CCTV <ชื่อ> … <img src="…">')`)
    ตามที่โครงการภายนอก SirawichDev/water-now บันทึกไว้ (`server/providers/cctv/dds-markers.json`, commit `f840b34` เมื่อ 28 ก.ย. 2569)
    แทนข้อมูลจากโครงการไม่เป็นทางการ 2 แห่งที่ใช้ก่อนหน้า (aracox/SceneFlow, maholan) ซึ่งพิกัดไม่ตรงกัน — เรายังเปิดหน้านี้เองไม่ได้

    ที่อยู่ภาพยังตอบอยู่ แต่ภาพใหม่สุดมี `Last-Modified` 28 ส.ค. 2569 คือภาพอาจหยุดอัปเดตแล้ว — แอปแสดงเวลาถ่ายจาก `Last-Modified`
    ภาพที่เก่ากว่า 1 วันจะแสดงจาง มีป้าย "ภาพเก่ากว่า 1 วัน" พร้อมวันที่ถ่าย จึงไม่ถูกอ่านเป็นภาพปัจจุบัน
  - รายชื่อ `camera_profile` ของ floodbangkok (`bma-floodcam`) ก็มีแถว "CCTV บางเขนใหม่" ที่ใช้หมุด (ที่ผิด) ของ DDS — probe v4 พิมพ์แถวที่ชื่อขึ้นต้นด้วย "CCTV " ไว้ตรวจ
  - สถานีที่จับคู่ไว้ในตารางแสดงคู่กับกล้องเสมอ (แม้ห่างเกิน 150 ม.) ถ้าสถานีนั้นมีในระบบ เวลา "ถ่าย" ใช้ `Last-Modified` ของไฟล์ภาพ
    (ไม่ใช้ถ้าล้ำเวลาเครื่องเกิน 5 นาที) แคชภาพ 60 วินาที เก็บในหน่วยความจำไม่เกิน 15 นาที
